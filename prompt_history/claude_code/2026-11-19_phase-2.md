**Key design decisions**
- One RNG stream per table (`master.parties`, `shipments.loggers`, …), so changing one generator never moves another's numbers.
- **Phase 2 output is a valid all-NORMAL baseline:** every dwell ≤ 120 min, every calibration covers its assignment, `carrier_reported_status = PASS`. Phase 3 scenarios will build on this, because LONG_DWELL and CALIBRATION_EXPIRED touch Phase 2 tables. This is flagged as an open question.
- The planner declares the version in force at `planned_departure_at`, so DECISIONS #26 mismatches around 1 July happen naturally.
- Trip times come from the haversine distance between the party cities, ordered via hub stops. Planned duration is clipped to `trip_duration_hours`.
- Devices are assigned greedily in time order (a loop over shipments, not readings). A random free device is picked whose calibration covers the window, with a turnaround buffer, so windows never overlap.
- Lot quantities are split per lot with a utilisation of < 100 %, so Σ shipped ≤ lot quantity by construction (and asserted).

**Risks:** Parquet byte-determinism (mitigated: CSV is the UAT checksum target); running out of devices or eligible lots (fail fast with `GenerationError`).
