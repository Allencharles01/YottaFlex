**Key design decisions**
1. **`run-all`** runs generate → inject → check → validate → validate (baseline) → evaluate → export in one process. It gives each stage exactly the command line the single command would record, so its output is byte-identical to running the stages by hand (I'll test this). It stops at the first failing stage, names it, and writes `run_summary.json` even when a stage fails.
2. **`reproduce`** runs the pipeline three times: run1 and run2 with the same seed, then a control run with seed + 1. Each run starts in an empty folder at one fixed path inside `output/<scale>/reproducibility/runs/`, and is moved aside to `run1/`, `run2/` or `control/` when it finishes.
   - Using one path means the provenance records, which name `--output-dir`, can be compared byte for byte too. Path independence of the data is already tested in Phase 7.
   - Every file is compared by sha256. The two exceptions are `manifest.json` and `run_summary.json`: they are compared on their content without the wall-clock and timing blocks, with the hash recomputed rather than read from the file.
   - Default is `--no-verify-sql`: identical SQL bytes give an identical load, and `run-all`/`export` still run the load proof by default.
3. **Peak memory per stage**: the process resets its own peak RSS through `/proc/self/clear_refs`, then reads `VmHWM`. Outside Linux it falls back to `ru_maxrss`, and the method used is recorded.
4. **Seed rule**: every seeded stage record must carry the same seed. This is a new rule 5 in `verify_chain`, with a unit test and a CLI test.

- The control seed must also pass the strict evaluation; if it doesn't, that is a real finding and I'll report it.
- The test suite will take about a minute longer (slow-marked).
